# v0.15.0 — everyday ledger, phase 3A

This release exposes existing split accounting in the transaction editor and adds
safe tools for organizing existing transactions. It is the first part of phase 3,
not completion of every item in the HomeBank roadmap.

## Included

- Create, load and replace expense split allocations with an exact total. Split
  children appear inside their parent editor, not as extra ledger rows. Category
  filters can find a parent through its allocations. Quick/bulk category assignment
  cannot silently flatten a split, and direct mutation of child rows is rejected.
- Payee, reference, comma-separated tags, cleared status and a payment-method field
  in transaction forms, including Dashboard quick entry. Transaction changes and
  metadata commit atomically. Imported bank identities survive replacements.
- Save and keep details for repeated entry. Duplicate opens a reviewable copy with
  allocations/payee/tags/payment method and today's date, resetting bank reference
  and cleared status. A copy is not posted until saved.
- Payee rename/default-category editing, merge with metadata reference repair and
  deletion of unused payees. Rename/merge/remove used tags by exact comma-delimited
  tokens; tag operations do not change transaction amounts.
- Persisted category parents, same-kind/cycle validation and category merge with
  repair of entries/splits, children, rules, schedules, payee defaults, transfer undo
  history and named filters. A merge stops if both categories have limits in the
  same budget; combine the limits first. Parentage is organizational: reports and
  budgets still show categories separately, without automatic parent rollups.
- Named account-backed transaction filters, included in backup/restore. The old
  browser-local remembered view remains available.
- Compound rules (primary condition AND up to eight extra conditions). Settings
  exposes optional account and amount constraints. Existing rule APIs support all
  existing match fields/operators as additional conditions. Existing one-condition
  rules retain their behavior.
- Review active rules against existing ordinary entries in Bookkeeping, then select
  changes to apply. Rechecks stale previews and excludes splits, transfers and
  reconciled entries. Type changes are explicit in review and refresh balances.

## Data and upgrade

Schema updates are additive and idempotent. Backup format 6 adds category parents,
payment methods, named views and compound-rule data. Versions 2–6 can be restored;
older Ledgerra versions cannot read a version 6 archive. Keep a database backup
before upgrading and preserve the PostgreSQL volume and data-protection keys.
No historical amounts are automatically inverted or reclassified during upgrade.

## Remaining phase 3 work

Reusable transaction templates, void/reminder posting states, a standalone catalog
of unused tags, a fully general compound-rule editor, shared report/ledger filter
execution and hierarchical report/budget rollups are not delivered here. Existing
payment methods are editable labels with suggestions, not a managed dictionary.
Future recurrence/forecasting, budget/report and FX phases remain separate.

## Validation

177 backend tests (8 domain and 169 API), 136 frontend tests, a production frontend
build and six PostgreSQL-backed Chromium workflows pass. PostgreSQL transaction
counts were unchanged by the additive schema initialization. The repository's
requested graph refresh was attempted, but `graphify` is not installed here.
